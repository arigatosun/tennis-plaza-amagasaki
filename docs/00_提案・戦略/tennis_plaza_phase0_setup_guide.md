# テニスプラザ尼崎 Phase0「計測基盤構築」手順書

対象作業者: 吉川（技術担当）
前提: GA4 既存導入済み（月約1,650訪問計測中）/ CV計測は現状ゼロ・未設定 / Search Console 未連携 / 404 月275回 / モバイル68%
ゴール: CVキーイベント6種・SC連携・utm基盤・404→301・採用管理シート・KPIダッシュボードを稼働させ、「数字が見える」状態にする。

方針サマリ（全体）:
- 実装は GTM（Googleタグマネージャー）経由を主軸とする。理由: HP本体のコードを毎回触らずトリガー追加でCVを増減でき、tel:クリックや外部リンククリックをコードレスで拾えるため。GTM未導入なら先にGTM導入（後述0章）。
- GA4ネイティブの「イベント作成 / 拡張計測」は、サンクスページ到達系・file_download系の補助手段として併用。
- 全CVは最終的に GA4管理 > キーイベント で「キーイベント」化して初めてCVとしてカウントされる。

## 1. CVキーイベント6種の実装

共通ルール:
- イベント名は GA4命名規約に従い「半角英小文字 + アンダースコア」で統一。
- 実装後は必ず DebugView で発火を確認 → GA4管理 > キーイベント で「キーイベント」トグルをON。
- 新規イベントは作成直後はキーイベント化候補に出ないことがある。1回でも発火させればイベント一覧に現れる。

| # | CV | イベント名（推奨） | 計測方法 | 主実装 |
|---|----|--------------------|----------|--------|
| 1 | 体験予約完了 | `trial_booking` | サンクスページ到達 | GTM(優先) or GA4ネイティブ |
| 2 | 問い合わせ送信 | `contact_submit` | フォーム送信完了 / サンクス到達 | GTM |
| 3 | 電話タップ | `tel_click` | tel:リンククリック | GTM |
| 4 | 入会フォーム到達 | `signup_form_view` | 入会フォームページ表示 | GTM or GA4ネイティブ |
| 5 | LINE登録クリック | `line_click` | 外部リンク（LINE）クリック | GTM |
| 6 | 資料DL | `file_download` | 拡張計測のfile_download | GA4拡張計測 + カスタムディメンション |

### 1-1. 体験予約完了 `trial_booking`（サンクスページ到達）

予約完了後に専用サンクスページ（例: `/trial/thanks/`）へ遷移する設計が前提。なければ制作側にサンクスページ追加を依頼する。

GTM実装:
- [ ] トリガー作成: タイプ「ページビュー」、条件 `Page Path` が `/trial/thanks/` を含む
- [ ] タグ作成: 「GA4イベント」タグ、イベント名 `trial_booking`、上記トリガー紐付け
- [ ] プレビューで該当URL表示時に発火確認 → GA4 DebugViewで確認

GA4ネイティブ実装（GTM使わない場合の代替）:
- [ ] 管理 > イベント > イベントを作成 > 作成
- [ ] カスタムイベント名 `trial_booking`、一致条件: `event_name` 等しい `page_view` かつ `page_location` 含む `/trial/thanks/`

確認後:
- [ ] 管理 > キーイベント で `trial_booking` をキーイベント化

### 1-2. 問い合わせ送信 `contact_submit`（フォーム送信）

サンクスページがある場合は1-1と同方式（`Page Path` = `/contact/thanks/`）。ない場合はフォーム送信トリガーを使う。

GTM（フォーム送信トリガー）:
- [ ] GTM変数で組み込み変数「Form ID」「Form Classes」を有効化
- [ ] トリガー作成: タイプ「フォームの送信」、対象の問い合わせフォームに限定（Form ID等で絞る）
  - ※検証チェックボックス（タグの待機/検証）を使い、誤発火・送信失敗時の発火を防ぐ
- [ ] タグ作成: GA4イベント `contact_submit`、上記トリガー紐付け
- [ ] フォームが ajax送信 / 外部埋め込み（formrun等）の場合は「フォーム送信トリガー」が効かないため、送信完了表示要素のクリック or サンクス遷移 or DataLayer push で代替（フォーム実装を要確認）
- [ ] DebugView確認 → キーイベント化

### 1-3. 電話タップ `tel_click`（tel:リンククリック）

モバイル68%のため最重要CVの一つ。`<a href="tel:...">` のクリックを拾う。

GTM実装:
- [ ] 組み込み変数「Click URL」を有効化
- [ ] トリガー作成: タイプ「クリック - リンクのみ」、条件 `Click URL` が `tel:` で始まる（正規表現 `^tel:` でも可）
- [ ] タグ作成: GA4イベント `tel_click`、パラメータに `click_url = {{Click URL}}` を付与（どの番号か判別用）
- [ ] スマホ実機 or DebugViewで電話リンクタップ → 発火確認
- [ ] キーイベント化

注意: 電話番号がテキスト表示のみ（リンク化されていない）箇所は計測不可。制作側に主要導線の番号を `tel:` リンク化するよう依頼すること。

### 1-4. 入会フォーム到達 `signup_form_view`（フォームページ表示）

入会フォームのページ（例: `/signup/` や外部フォームURL）の表示を計測。

GTM実装:
- [ ] トリガー作成: タイプ「ページビュー」、条件 `Page Path` が `/signup/` を含む
- [ ] 外部フォーム（Googleフォーム等）に飛ぶ場合は「到達」ではなくクリック計測に切替: タイプ「クリック-リンクのみ」、`Click URL` がフォームURLを含む
- [ ] タグ作成: GA4イベント `signup_form_view`
- [ ] 確認 → キーイベント化

### 1-5. LINE登録クリック `line_click`（外部リンククリック）

公式LINEは現状未開設。開設後にLINE友だち追加URL（`https://lin.ee/...` または `https://line.me/...`）を控えてから実装。

GTM実装:
- [ ] 組み込み変数「Click URL」有効化
- [ ] トリガー作成: タイプ「クリック-リンクのみ」、条件 `Click URL` が `lin.ee` または `line.me` を含む（正規表現 `lin\.ee|line\.me`）
- [ ] タグ作成: GA4イベント `line_click`、パラメータ `click_url = {{Click URL}}`
- [ ] 確認 → キーイベント化

備考: 拡張計測の「離脱クリック」でも `click` イベントとして取れるが、CV専用に名前付きイベントを切る方がキーイベント化・ダッシュボード集計が明確。

### 1-6. 資料DL `file_download`（拡張計測 + カスタムディメンション）

GA4拡張計測の「ファイルのダウンロード」を使う（pdf/docx/xlsx/zip等の拡張子クリックを自動計測）。

- [ ] 管理 > データストリーム > ウェブ > 拡張計測機能 で「ファイルのダウンロード」がONか確認
- [ ] 資料DLリンクが標準対象拡張子か確認（pdf, xlsx, docx, pptx, zip 等）。`.pdf`直リンクが基本対象。
- [ ] DebugViewで `file_download` 発火確認
- [ ] 管理 > キーイベント で `file_download` をキーイベント化

★現状の問題への対処（重要）:
`file_download` は発火しても、どのファイルがDLされたかを示す `file_name` / `file_extension` パラメータがレポート画面では「(not set)」相当で中身が見えない。これはイベントパラメータをカスタムディメンションに登録していないため。以下で対処する。

- [ ] 管理 > カスタム定義 > カスタムディメンションを作成
  - [ ] ディメンション名: `file_name` / 範囲: イベント / イベントパラメータ: `file_name`
  - [ ] 同様に `file_extension`、必要なら `link_url` も登録
- [ ] 登録後、レポート（探索）で `file_name` 別の `file_download` 件数が見えることを確認
  - ※カスタムディメンションは登録時点以降のデータにのみ反映。過去分は遡及しないため早期登録する。
- [ ] 標準拡張子でない資料（フォーム遷移型・独自DL）がある場合はGTMでクリックトリガーを別途作成し `file_name` を手動付与

## 3. utm 命名規則

目的: Instagram経由LP到達25/月→260/月（10倍）を「正しく」計測するため、流入元を統一ルールでタグ付けする。

基本原則:
- 全て半角英小文字、スペース禁止（区切りはハイフン）。表記ゆれ厳禁（`Instagram`/`IG`/`insta` 混在NG → `instagram` に統一）。
- `utm_source` = どこから（媒体名） / `utm_medium` = 流入種別（広告か自然かオフラインか） / `utm_campaign` = 施策名（日付や目的）。
- 採用施策は campaign に `recruit` を含めて集客と区別する。

命名テーブル（採用フェーズ標準）:

| 流入元 | utm_source | utm_medium | utm_campaign 例 |
|--------|------------|------------|-----------------|
| Instagram投稿/プロフ | instagram | social | recruit_ig_2026q3 |
| Instagram広告(Paid) | instagram | paid-social | recruit_ig_ad_2026q3 |
| doda等 求人媒体 | doda | cpc | recruit_doda_2026q3 |
| その他媒体 | （媒体名） | cpc | recruit_（媒体）_2026q3 |
| チラシ（QR） | flyer | offline | recruit_flyer_amagasaki_2026q3 |
| 公式LINE | line | social | recruit_line_2026q3 |
| X(@tennipla) | x | social | recruit_x_2026q3 |
| メール/署名 | newsletter | email | recruit_mail_2026q3 |

URL例:
`https://tennisplaza.jp/recruit/?utm_source=instagram&utm_medium=social&utm_campaign=recruit_ig_2026q3`

運用ルール:
- [ ] utm付与は手書きせず「採番表（スプレッドシート）」で一元管理し、URLビルダーで生成（GA4 Campaign URL Builder）
- [ ] チラシは専用の短縮URL+QRコードを発行（`utm_source=flyer`固定、配布先別に campaign を分ける: `recruit_flyer_school_a` 等）
  - [ ] 配布先ごとにcampaignを分けると「どのチラシが効いたか」が分かる
- [ ] SNSプロフィールリンクにもutmを必ず付与（Instagramプロフのリンクが現状HPに繋がっていない問題の解消も同時に行う）
- [ ] paid-social は「誰が出稿か不明なPaid Social」と区別するため、自社出稿分は必ずこのutmを通す

## 4. 404特定 → 301リダイレクト

現状: 404エラー月275回。検索流入が良質なだけに、404はSEO資産とCV機会の流出。

### 4-1. 404の発生元特定

GA4側:
- [ ] レポート > エンゲージメント > ページとスクリーン
- [ ] 「ページタイトル」ディメンションで 404ページのタイトル（例:「ページが見つかりません」「404」「Not Found」）を検索フィルタ
- [ ] そのタイトルに該当する `ページパス + クエリ文字列` を表示し、404が発生しているURL一覧を抽出
- [ ] 補助: 探索レポートでディメンション「ページタイトル」「ページパス」、指標「表示回数」を組み、404タイトルで絞り込む
- [ ] 可能なら GTMで「page_not_found」イベントを別途切ると正確（404テンプレートに専用trueデータレイヤー or タイトル一致トリガー）

Search Console側（連携後）:
- [ ] SC > インデックス作成 > ページ > 「見つかりませんでした(404)」レポートでGoogle検出の404 URL一覧を取得
- [ ] 「参照元」を見てどこからのリンクで404になっているか確認

### 4-2. 301リダイレクト設定方針

- [ ] 抽出した404 URLを「正しい遷移先」とマッピングする一覧表を作成（旧URL → 新URL）
  - 後継ページがある → 該当ページへ301
  - 後継なし・統合済み → 関連カテゴリTOP or サイトTOPへ301（安易な全件TOP送りは避け、文脈の近いページへ）
- [ ] 301の実装場所はサーバ環境に依存（要確認）:
  - Apache: `.htaccess` に `Redirect 301 /old /new`
  - Nginx: `return 301`
  - WordPress等CMS: リダイレクトプラグイン or 管理機能
- [ ] 内部リンク・サイトマップ側の旧URL参照も修正（リダイレクト依存を減らす）
- [ ] 設定後、旧URLアクセスで新URLに301で飛ぶことを確認（ブラウザ開発者ツールのNetworkでステータス301を確認）
- [ ] 数週間後にGA4の404件数 / SCの404レポートが減少しているか再確認

注意: tel:番号誤り・外部からの古いリンク由来など「自社で直せない404」も混在する。発生回数の多い順に対処し、上位を潰せば275回の大半が消える想定。

## 5. 採用管理シート / KPIダッシュボード 項目

### 5-1. 採用管理シート（候補者トラッキング）

1候補者=1行。GA4のCVと突き合わせるための流入元列を必ず持つ。

- [ ] 候補者ID / 応募日 / 氏名（イニシャル可）/ 応募職種（社員 or バイト）
- [ ] 流入チャネル（instagram / doda / hp-seo / flyer / line / x）※utm_sourceと一致させる
- [ ] utm_campaign（どの施策経由か）
- [ ] ステータス（応募 / カジュアル面談 / 最終 / 内定 / 承諾 / 辞退・不採用）
- [ ] 各ステータス日付（カジュアル面談日 / 最終日 / 内定日 / 承諾日）
- [ ] 担当（中村=採用管理 / 中田 等）
- [ ] 辞退・見送り理由（歩留まり改善の材料）
- [ ] 待遇提示内容（MTGで確定後に列追加）
- [ ] 備考（AIスカウト経由は最終送信が人である旨を担保するメモ列）

法務メモ列の運用: 候補者紹介の成功報酬（職業紹介事業）に該当する取り扱いはしない。AIスカウトは半自動・最終送信は人が行った記録を残す。

### 5-2. KPIダッシュボード（90日North Star進捗）

採用ファネル（確定設計）に沿って実数を毎週更新:

- [ ] North Star進捗: 社員1+バイト2 採用完了数 / 目標3、近江の現場固定シフト離脱状況
- [ ] ファネル実数 vs 目標（90日累計）:
  - LP到達 / 650
  - 応募 / 50
  - カジュアル面談 / 22
  - 最終 / 9
  - 内定 / 5
  - 承諾 / 3
- [ ] 各段階の実歩留まり（実績%）と仮置き値（LP→応募8% など）の乖離
- [ ] チャネル別LP到達数 vs 配分目標（Instagram40% / 媒体30% / HP-SEO20% / チラシ10%）
- [ ] Instagram経由LP到達: 月次推移（現状25 → 目標260）
- [ ] GA4 CV6種の発生数（trial_booking / contact_submit / tel_click / signup_form_view / line_click / file_download）
- [ ] SC: 求人/ブランド関連クエリの表示回数・クリック数
- [ ] 404発生回数の週次推移（減少トラッキング）

データ連携:
- [ ] GA4 → Looker Studio接続でダッシュボード自動化を推奨（手集計を減らす）。最低限はGA4探索のブックマークでも可。
